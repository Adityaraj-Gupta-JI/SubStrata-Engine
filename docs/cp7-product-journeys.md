# CP7 product integration

## Implemented journeys

- `/onboarding` resumes from the authenticated user's session-scoped organization/workspace/database selection. Completion is derived from the current authorized catalog, not trusted client flags. Organization/workspace creation reuses the sidebar's actual API forms; mobile setup links open and focus that navigation. Managed provisioning and provider-specific BYODB forms remain on `/databases` with their real permission/configuration checks. Optional OpenRouter setup links to `/settings/ai`.
- Explorer relationship browsing loads authorized catalog metadata, never table rows for the graph. Choose a schema, page through at most 12 tables at a time, select a table using the graph or keyboard-accessible buttons, inspect PK/FK columns and follow a relationship to real table details. Requests are sequential to bound database connection concurrency. Cross-page edges remain listed. Cross-schema edges are excluded; existing metadata limits fail with a controlled error rather than suggesting a complete large schema.
- PostgreSQL and MySQL relation responses now include structured, column-level `foreignKeys`. PostgreSQL restricts target names to the approved schema and readable target tables. MySQL restricts targets to the approved database, where its verified role has schema-wide SELECT. Composite foreign keys retain their constraint names and column ordering. No SQL definitions are parsed in the browser.
- Explorer table details hand off a dialect-quoted, bounded SELECT draft to `/sql-editor`. The query does not run on navigation. Selected schema/table restore from the URL fragment on refresh; access and existence are checked again. Workspace/database IDs restore from session storage. SQL drafts survive in-app navigation in memory, but deliberately do not persist SQL text or approval tokens to browser storage.
- Dashboard displays the real catalog, managed/external/dialect/status labels, persisted database audit outcomes, private conversations and agent runs. Refresh reloads current state; failures in one activity source do not hide successful sections or fabricate empty-state success.
- Dashboard conversation and execution links carry an exact record ID in a URL fragment. Chat reloads the saved conversation and its bound database; agent history reloads persisted traces/status/usage. Agent traces link back to their original conversation for SQL proposal review. Chat links to the existing authorized agent configuration/run workflow. These links never start a provider request or execution automatically.
- Existing chat model selection, streaming, cancellation, provider errors, usage, SQL proposals and human approval flow are reused. Reload failures clear loaded messages/traces. PostgreSQL change preview/approval remains separate from read execution; MySQL stays read-only. No live opt-in, provisioning, credentials or permissions were changed.

## Acceptance limits

This checkpoint connects existing product capabilities; it does not prove a hosted rollout. Genuine Clerk/OpenRouter browser acceptance, a real Neon provisioning journey, R2 cloud bindings, mobile visual acceptance and hosted networking were **not exercised**. Existing Clerk cryptographic tests remain distinct from mocked authenticated journey tests. OpenNext still warns about Windows compatibility and experimental Node middleware; Node tests retain experimental transform/SQLite warnings.

Owner-configured infrastructure and approved credentials are required for live managed provisioning, public BYODB connectivity and AI requests. PostgreSQL writes still require verified separate roles, owner opt-in and exact per-query approval; none was enabled in a live environment. MySQL writes, cross-schema relationship visualization, arbitrary/complex SQL and automatic AI execution remain unavailable. Onboarding reuses the existing provider forms rather than introducing a second connection implementation. A fresh browser session requires selection again; no SQL or secret is persisted to local/session storage.

For manual acceptance, start the existing local API and frontend using their documented development commands, sign in normally, open `/onboarding`, create/select a workspace, connect/select an approved disposable database, inspect relationships and records, hand a SELECT to the editor and run it explicitly. Open a saved chat from Dashboard, generate a proposal, review it in SQL, then configure/run an authorized agent and follow its saved trace back to the conversation. Refresh explorer/chat/trace routes and verify context; revoke a fixture membership and reload to verify controlled denial. Do not enable live writes/provisioning for this procedure without separate owner approval.
