# CP6 database management and approval workflows

## Functionality

PostgreSQL changes use separate `/change-preview` and `/change-execute` endpoints. The read-only `/query` endpoint is unchanged. Supported changes are explicit VALUES inserts, constant/parameter assignments in UPDATE, DELETE, explicit CREATE TABLE columns/constraints, one supported ALTER TABLE operation, one DROP TABLE without CASCADE, and column-only CREATE INDEX. Unsupported syntax, functions, casts, subqueries, privilege commands, cross-schema references and multiple statements are rejected by an explicit PostgreSQL AST allowlist. SQL executed is the parser's canonical statement, with transaction-local `standard_conforming_strings=on` and `search_path=pg_catalog` to pin parser/server semantics. Parameters are independently bounded and included in the approval digest.

The schema editor creates SQL previews for table creation, adding/removing columns, supported type and NOT NULL changes, primary/foreign key creation and constraint removal, indexes and table removal. The record editor uses the existing paginated grid, typed/nullable inputs, explicit column inclusion and original primary-key values for parameterized updates/deletes. Composite keys are supported; editing/deletion without a complete key is blocked. Large integers remain text. Unsupported types are not editable. There is no optimistic row-version locking: refresh before editing shared records; concurrent record edits can overwrite earlier values.

AI chat and SQL assistance understand the selected PostgreSQL/MySQL dialect, explain queries and classify risk. PostgreSQL SELECT, DML and schema changes may be proposed and edited; MySQL proposals remain SELECT-only. A proposal tool has no execution capability. The human must request a server preview and explicitly confirm a change. No agent or AI route calls the change execution service.

## Authorization and approvals

- Assigned workspace roles retain read access. Owners/admins/members may request enabled record inserts. Owners/admins may request supported schema administration. **All UPDATE and DELETE statements require owner approval**, including primary-key-filtered changes, as a conservative initial policy. Destructive schema changes also require an owner. No SQL WHERE clause is treated as proof that a mutation is bounded.
- Writes are disabled by default, separately for every database, including BYODB. Only an effective workspace owner can register approved execution credentials and opt in. Enabling access verifies the actual PostgreSQL roles. No write role is inferred from a read credential and no provider resources or roles are automatically created.
- Preview issues a cryptographically random 256-bit token, valid for 60 seconds. Only its SHA-256 digest is stored in D1. It binds canonical SQL plus parameters, target database, user, current effective role, permission version, write-access revision, credential reference and approved destination fingerprint. Membership changes, even if later reversed, invalidate outstanding approvals through database triggers. User/organization changes are versioned too.
- Execution atomically consumes the token and records the attempt/audit in a D1 transaction before opening the PostgreSQL change transaction. Concurrent replay has one winner. Consumption is permanent even if execution fails. Elevated operations require typing `APPLY <actual-database-name>`; other changes require `CONFIRM`, plus frontend acknowledgement.
- PostgreSQL uses BEGIN/COMMIT/ROLLBACK, hostname-verified TLS to an administrator-pinned public IP, a 3-second statement deadline, 500ms lock timeout and 5-second idle transaction timeout. More than 1000 affected rows causes rollback. No RETURNING row payloads are accepted; execution returns bounded status, row count and elapsed time.
- Permission/configuration checks run again before the statement and before commit. D1 and PostgreSQL are separate systems: there is no distributed atomic commit or instantaneous revocation guarantee after the final permission check. Already-running bounded transactions can finish during that narrow race. A lost connection/worker crash after token consumption is never automatically retried; history records or reconciles an **unknown** outcome. Inspect the actual target before manually retrying. An audit failure after database commit may likewise leave an unknown client outcome.
- History and audit records contain operation, risk, status and SQL digest, not SQL values, passwords, tokens or connection strings. Credentials remain server-side. Errors never echo driver errors or SQL parameters.

## Owner setup for PostgreSQL (not performed against any external provider)

1. Keep `METADATA` and the existing encrypted-object `TENANT_CREDENTIALS` R2 binding. Apply migrations 0006–0008 to the selected local database. Cloud migrations and resource creation are not authorized by this checkpoint.
2. Supply independent Worker-only `SQL_VAULT_KEYS` (JSON key-ID to 64 lowercase hexadecimal characters) and `SQL_VAULT_KEY_ID`. Never reuse Neon/BYODB/AI wrapping keys or expose them in `NEXT_PUBLIC_` variables. Do not paste keys into a chat.
3. Have the database owner prepare distinct restricted read, writer and schema-administration roles for the exact database/schema. Existing read roles remain read-only. Execution roles must have NOINHERIT, no superuser/CREATEDB/CREATEROLE/replication/BYPASSRLS, no other role memberships, no database CREATE/TEMP, no write/create privileges outside the approved schema, and no unsafe extensions, user routines, foreign servers, user triggers/rules or cascading/SET NULL/SET DEFAULT foreign-key actions. Managed roles must lack CONNECT on other databases. A writer has schema USAGE and the exact required table SELECT/INSERT/UPDATE/DELETE permissions, without TRUNCATE or schema ownership/CREATE. A schema administrator owns the approved schema and has CREATE there, but is not a cluster administrator. It can alter/drop only objects PostgreSQL itself permits. Existing tables owned by another role require the database owner's separate ownership review. Do not grant broad cluster or PUBLIC privileges to make verification pass.
4. Add both execution role names and the database/schema to a reviewed `BYODB_ALLOWED_DESTINATIONS` public-IP pin. For an external connection, this must be the same approved destination and fingerprint as the existing connection; revalidate the read connection after changing its allowlist. Changing a pin or role list invalidates existing connections/approvals until reviewed. No arbitrary host, connection string, TLS override or private-network destination comes from a user request.
5. Supply Worker-only `DATABASE_EXECUTION_TARGETS`, a nonsecret JSON array. Replace all placeholders with approved values, using a new random UUID per immutable credential reference:

```json
[
 {"databaseId":"32_HEX_DATABASE_ID","capability":"write","destinationId":"approved-endpoint","role":"restricted_writer","reference":"sql-role/UUID_FOR_WRITER","readRole":"existing_read_role","writeRole":"restricted_writer"},
 {"databaseId":"32_HEX_DATABASE_ID","capability":"admin","destinationId":"approved-endpoint","role":"schema_administrator","reference":"sql-role/UUID_FOR_ADMIN","readRole":"existing_read_role","writeRole":"restricted_writer"}
]
```

6. Sign in as an owner, select the database, and open **Write access and execution history** in Databases or SQL. Under role registration, supply each approved role password privately and type `REGISTER <actual-database-name>`. The server disables writes, encrypts the password into an immutable R2 object and verifies the role. It never returns credentials. Failed verification tombstones the new object. Once both roles verify, type `ENABLE <actual-database-name>` and explicitly enable access. BYODB requires this same per-database owner opt-in; existing connection credentials alone cannot enable writes.
7. Rotation uses a newly approved role/reference in configuration, private password registration, verification and a new explicit opt-in. Removing configuration, keys or objects fails closed. Retain old wrapping keys while rotating credentials to new references; remove old keys only after reviewing all references. Disable access and reconcile/tombstone retired encrypted objects before retiring old roles. There is no public PostgreSQL role-deletion or destructive provider endpoint. Crashes before metadata/storage reconciliation can leave encrypted orphan objects requiring owner maintenance.

## MySQL BYODB

The adapter uses `mysql2` 3.24.6 with the existing Workers `nodejs_compat` target and required `disableEval: true` static result parsers. The real database tests assert that setting. A constrained socket connects directly to the approved public IP while `mysql2` retains the approved hostname for certificate verification. TLS is mandatory and verified before authentication. Multiple statements and LOCAL INFILE are disabled. The adapter requires MySQL 8+, no active roles, and only USAGE plus SELECT on the one approved database. Any additional privilege fails closed. Reads run in read-only transactions with a 3-second server execution timeout, 5-second connection-operation deadline, server-side JSON/cell truncation before buffering, and 100-row/60KB budgets and bounded metadata queries. The SQL editor uses a separate MySQL tokenizer/grammar; no PostgreSQL AST is reused. It supports column/asterisk SELECT, literal AND comparisons, one-column ordering, LIMIT and OFFSET. Row reads are limited to InnoDB base tables with 1–100 supported column names; views and other engines are denied pending a separate security review. This prevents SECURITY DEFINER view escapes into another database. Functions, joins, comments, escapes, parameters, writes, DDL, INTO OUTFILE and multiple statements are unavailable.

Owner configuration:

- Supply independent Worker-only `MYSQL_VAULT_KEYS` and `MYSQL_VAULT_KEY_ID` and the existing R2 binding.
- Set `MYSQL_ALLOWED_DESTINATIONS` to the same nonsecret destination shape as PostgreSQL, with **port 3306**, reviewed public IP/hostname, database names, restricted roles, and `schemas` containing the approved database name. Never supply a private address or disable TLS verification.
- In the separate MySQL section of Databases, choose an approved endpoint/database/role and privately enter its password. Validation checks the actual encrypted connection and SHOW GRANTS before saving. Credentials use a separate keyring and authenticated org/workspace/database/role/`mysql-read` scope. D1 contains opaque references only. Rotation validates a new immutable object/reference; disconnect disables access before tombstoning the encrypted object. Neither action modifies the external database/role.
- Select the MySQL source for Explorer, paginated rows, read-only SQL and AI schema context. PostgreSQL write approvals are never accepted for MySQL.

Cloudflare documents `mysql2` for Workers with Hyperdrive, but no Hyperdrive resource is created here. Direct pinned-socket transport still requires hosted development acceptance before any production rollout: https://developers.cloudflare.com/hyperdrive/examples/connect-to-mysql/mysql-drivers-and-libraries/mysql2/

## Validation boundaries

Approval tests use real disposable D1 with mocked identity/role verification/execution, explicitly labelled. PostgreSQL gateway tests use a real owned disposable local TLS database, distinct roles, real encrypted R2 credentials, owner registration/opt-in, transaction success and rollback, affected-row limits, read regressions and cross-tenant denial. MySQL integration uses an opt-in owned disposable TLS instance (native executable or container). The successful local run used the already-installed MySQL 8.4.9 Windows binary with --no-defaults, an independently initialized data directory, an owner marker, a verified @@datadir, a private test certificate and a temporary loopback-only port. It never connected to an existing MySQL service. Test factories assert the production public-IP/TLS configuration and map it only to the local fixture. Those tests do not prove hosted runtime behavior. No genuine Clerk/OpenRouter browser acceptance or cloud provider database operations are claimed.
